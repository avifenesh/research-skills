# Badges and venue rules

Use when choosing which badge to aim for, reading a call for artifacts, or checking the repo against ACM, MLSys, OSDI, USENIX Security, SOSP, ASPLOS or NeurIPS rules.

Dated facts are as of 2026-10-08. Re-read the call before you submit.

## ACM badges, version 1.1 (2020-08-24, labelled "Current") [acm-badging]

ACM defines an artifact as a digital object created for or generated by the study: software, scripts, input datasets, raw data, analysis scripts. Terminology follows NISO: Reproducibility = different team, same setup; Replicability = different team, different setup.

| Badge | Policy text | What it means for the repo |
|---|---|---|
| Artifacts Evaluated: Functional | "documented, consistent, complete, exercisable, and include appropriate evidence of verification and validation". Documented = inventory plus enough description to run. Consistent = relevant to the paper and contributes to main results. Complete = all components relevant to the paper; proprietary parts need not be included but must be documented with how to obtain them, and "proxies for proprietary data should be included". Exercisable = scripts run, data can be accessed | README with inventory, one command per result, a proxy dataset if real data is private |
| Artifacts Evaluated: Reusable | Everything in Functional, plus "very carefully documented and well-structured" for reuse; community norms "strictly adhered to" | Installable package, stable CLI or API, configs separate from code, tests, license, docs |
| Artifacts Available | On a publicly accessible archival repository with a DOI or unique identifier and a declared plan for permanent access. Publisher, institutional or open repositories such as figshare or Dryad qualify; "Personal web pages are not acceptable". Need not be complete or evaluated | A Zenodo (or Software Heritage, figshare, Dryad, institutional) record of a tag |
| Results Validated: Reproduced | Main results obtained by another person or team "using, in part, artifacts provided by the author" | Your scripts work for someone else on comparable hardware |
| Results Validated: Replicated | Main results obtained independently, without the author's artifacts | The paper describes the method well enough; code alone is not sufficient [raff] |

Tolerance: exact replication or reproduction "is not required, or even expected"; results must agree "to within a tolerance deemed acceptable", and differences "should not change the main claims" [acm-badging].

## Venue rules (as of 2026-10-08)

| Venue | Badges | Archive rule | Appendix or README rule |
|---|---|---|---|
| MLSys 2026 [mlsys26-ae] | Availability, Functional, Reproducible; a few Distinguished Artifact Awards | Public GitHub-or-similar link for reviewers | Artifact abstract with minimal hardware and software, how it supports the paper, how to validate, expected result; appendix attached to the paper PDF. Optional, separate from acceptance. Single-blind, anonymous reviewer interaction. Submission 2026-03-08 20:00 UTC, review to 2026-04-08, results 2026-04-16. MLSys 2027 dates were not published when fetched |
| OSDI '26 [osdi26-ae] | Available only | Zenodo (DOI), institutional, FigShare, Dryad, Software Heritage, GitHub, GitLab; no personal pages | README with Getting Started (about 30 minutes, "Hello world"-sized) and Detailed instructions; optional 2-page appendix. Artifact deadline 2026-05-08, decisions 2026-06-01. Single-blind |
| USENIX Security '26 [sec26-ae] | Available, Functional, Reproduced | Final archive must support versioning; Zenodo recommended; GitHub and GitLab prohibited | Appendix of at most 3 pages with the claims list and how to compare results with the paper |
| SOSP '23 via sysartifacts [sosp23-badges] | Available, Functional, Reproduced | Public site "with a specific version such as a git commit" | Functional: README, environment spec, build and run instructions, same terminology as the paper. Reproduced: exact environment, precise command per claim, resource needs per claim, dependencies from established sources |
| ASPLOS 2027 [asplos27-appendix] | Via a cTuning-style appendix | Not stated in the fetched page | Five obligatory sections; "maximum allowable variation" stated (see `reproduce.md`) |
| NeurIPS main track [neurips-checklist][neurips-code-policy] | None; a checklist, not badges | Anonymized code at submission | Item 5: "exact command and environment needed to run to reproduce the results"; "no because proprietary" is acceptable |

The archive rules disagree on GitHub: OSDI '26 lists it; USENIX Security '26 and the cTuning checklist exclude it for the final archive [osdi26-ae][sec26-ae][ctuning-checklist]. Safe default: GitHub for development, a Zenodo release with a DOI for the badge (design).

## NeurIPS checklist items that touch the repo [neurips-checklist]

| Item | Asks for |
|---|---|
| 4 | Steps taken to make results reproducible or verifiable |
| 5 | Code, data and instructions; the "exact command and environment"; anonymized at submission |
| 8 | Compute: CPU or GPU type, internal cluster or cloud, memory and storage, per run and total, including failed experiments |
| 11 | Safeguards for high-risk releases: usage guidelines, gating |
| 12 | Cite the creators of every asset; state license name (for example CC-BY 4.0) and version; terms of service for scraped data |
| 13 | Document new assets with structured templates; consent; anonymized at submission |

NeurIPS 2026 Evaluations & Datasets track (renamed from Datasets & Benchmarks): Croissant metadata is mandatory (core plus Responsible AI fields); preferred hosts are Harvard Dataverse, Kaggle, Hugging Face and OpenML; datasets over 4 GB need a sample for reviewers; non-compliance can mean desk rejection [neurips26-ed-hosting][neurips26-ed-call].

## Pineau v2.0 and Papers with Code

- Pineau v2.0 (2020-04-07) splits the paper checklist from a code checklist, since "the paper and the code are two separate research artefacts". Code items: dependencies, training code, evaluation code, pre-trained models, README with a results table and the precise command per result [pineau-checklist].
- NeurIPS 2019 numbers: code at submission 40% (ICML 2019: 36%), at camera-ready 74.4% (ICML 2019: 67%); 173 papers claimed in the reproducibility challenge; reviewers found the checklist useful in 34% of cases [pineau-2019].
- Papers with Code ML Code Completeness Checklist: (1) dependencies, (2) training code, (3) evaluation code, (4) pre-trained models, (5) README with a results table and commands [pwc-code]. Meta shut the site down in July 2025 and it redirects to Hugging Face; the GitHub repo with the checklist was still online on 2026-10-08 [pwc-shutdown][pwc-code].

## Choosing the target (design)

1. Every paper repo should pass Functional and Available: they need no second team.
2. Aim for Reproduced when the main claims are orderings and ratios that survive a hardware change; ship the checker that proves it on the evaluator's box (`reference-results.md`).
3. Reusable is a property of the package, not the paper: installable, adapters, tests, docs. Decide early; it is costly to add after.
